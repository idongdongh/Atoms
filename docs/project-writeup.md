# Atoms 项目全景：实现思路、完成度、AI Coding 实践与扩展路线

> 配套阅读：[SUBMISSION.md](../SUBMISSION.md)（笔试交付精简版）· [docs/README.md](README.md)（文档索引）。本文是完整叙述版。

## 一、实现思路

**产品定位**：用一句话描述想法，Agent 在隔离工作区把它变成可运行、可发布、带数据库的全栈应用——参考 Atoms/Dyad 的体验，按多用户 Web 系统从零设计。

### 架构：三平面分离，契约先行

```
Control Plane（API）     会话、多用户隔离、预览/发布网关、SSE 事件流
Workspace Plane          每项目独立 Git 工作区（代码事实来源）+ 写锁
Execution Plane（Worker）Agent 工具循环、预览生命周期、受控构建
```

三平面通过 **Zod Schema 契约**通信（运行时校验，不只靠 TS 类型），数据库只存元数据（项目/消息/运行/版本索引），任何时刻都能从 Git 工作区 + 事件流重建审计。笔试交付采用单机 Demo 拓扑（[ADR 0005](adr/0005-demo-runtime-topology.md)），每个取舍都写明了企业级演进路径（容器拆分 → 状态外移 → Firecracker 沙箱集群）。

### 核心机制

| 机制       | 做法                                                                                                                                                           |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Agent 循环 | 8 个结构化工具（Zod 双端校验）、20 步预算、文件清单随系统消息注入、模型调用自动重试、SSE 逐 token 流式、每轮成功自动 commit                                    |
| 生成质量   | 对标 Dyad 的提示词工程（预览意识/技术栈规则/导入完整性检查/批量写指导）+ 模板预置 Tailwind v4 与 lucide-react                                                  |
| 预览网关   | dev server 以 `--base=/p/<id>/` 受控启动，空闲 10 分钟回收、打开即唤醒、启动重试、部署后自愈                                                                   |
| 全栈生成   | Agent 调 `db_create_table`（标识符/类型白名单 + 项目随机前缀 + RLS 行级安全），前端 anon key 直连 Supabase，service_role 仅 worker 持有且受 DDL 白名单函数约束 |
| 发布与回退 | 受控 `vite build` → 不可变 release 目录 → 激活指针原子切换 → 任意历史版本秒级回退，附扫码分享                                                                  |
| 安全边界   | scrypt 口令 + 会话隔离、子进程环境白名单（模型密钥绝不进生成应用）、`x-atoms-client` 头防 CSRF、发布静态服务路径穿越防护                                       |

### 关键取舍

照搬 Dyad 验证过的机制（dev server 预览、每轮一 commit、非破坏性回滚），把执行面从 Electron 本地搬到服务器并加上多用户隔离与脚本白名单；Dyad 的 Vercel 发布替换为自有不可变 release 链（Atoms/Lovable 模式）。Demo 用 SQLite/本地文件而非 Postgres/S3——契约不变，可平滑替换。已知取舍（`/p/` 未做签名鉴权等）在 SUBMISSION.md 如实披露。

## 三、AI Coding 工具使用说明

本项目是 **AI coding agent 主导开发、人负责决策与验收**的完整实践：两天内从架构规划到线上可用，全部代码、测试、部署产物、文档由 agent 完成，Git 历史（40+ commits）完整保留了人机协作过程。

### 项目侧的配合设施（让 AI 高效且不跑偏的关键）

1. **`AGENTS.md` 协作规则**：把架构硬约束写成 agent 指令（"Control Plane 不得执行用户代码"、"每项目同时最多一个写 Run"、"密钥不得入库"等十几条），agent 每次动代码前都会读到。
2. **ADR 文档先行**：重大取舍先写架构决策记录（6 篇）再动代码，agent 的实现始终有据可依。
3. **可验证的完成标准**：`pnpm check` = 格式 + 类型 + 70 测试 + 构建，任何改动以全绿为验收线；任务一律转成"先写测试再通过"的目标。
4. **Todo 跟踪 + 上下文压缩**：长任务用 todo 列表维持进度，上下文接近上限时先固化状态再继续。

### 四类典型用法（均有实例）

- **规划**：让 agent 通读代码库与笔试要求，产出第二阶段开发计划，人工审后按里程碑执行。
- **对抗式审查**：阶段完成后让 agent 以攻击者视角重审自己的代码——两轮共挖出 15+ 个并发/安全/部署问题（如 SSE 路由前缀错误导致生产断流、表名可从公开 URL 推算导致跨租户数据读写），全部修复并补回归测试。**AI 审 AI 写的代码**是本项目质量的主要保障手段。
- **端到端验证**：agent 直接驱动真实浏览器完成注册→生成→预览→发布→删除的 GUI 级验收，抓出了 curl 测不出的 bug（如纯 HTTP 环境下 `crypto.randomUUID` 不存在导致消息发不出去）。
- **运维与调试**：SSH 到生产服务器部署、读日志、查数据库定位问题；疑难 bug 走"复现→二分定位→修复→回归"闭环（如 vite base 与代理前缀的循环重定向问题）。

### 经验总结

- 给 AI **可验证的目标**（测试全绿、实测数据）比给描述性要求有效得多。
- **约束写在指令里**（AGENTS.md）比每次对话口头强调可靠。
- AI 的产出需要**独立的验证回路**（对抗审查、浏览器实测、生产冒烟），尤其是部署链路——本项目所有严重 bug 都出在"没有实测过的路径"上。
- 人最有价值的三件事：**定取舍**（如无域名走 IP 直连）、**控范围**（砍掉超出笔试要求的功能）、**判优先级**（先修阻断交付的）。
